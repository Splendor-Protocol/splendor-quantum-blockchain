# QRC-721: non-fungible tokens (`qrc721_v1`)

One id, one owner. `vm/qrc721.go` had been written and tested but reachable
by nothing; `qrc721_v1` routes it whole through the module router, the way
`qrc1155_v1` routed the multi-token standard. Every write is a `TxCall` to
`vm.ModuleRouterAddress` carrying

```json
{"module":"qrc721","action":"…","params":{…}}
```

and requires `module_revert_v1` no later than itself (a failed action is a
failed receipt, fee kept, nonce consumed).

## Ownership

**Deploy is open. Mint on someone else's collection is not.** The deployer is
recorded as the collection owner at deploy, and `mint` refuses every other
caller — Alice's collection stays Alice's supply; Bob deploys his own if he
wants to mint. This is the rule ERC-721 collections use and the one QRC-20
and QRC-1155 already follow here. Collections deployed through the Go API
before this rule have no owner slot and therefore cannot be minted on by
anyone; none exist on a live tier, because nothing could reach the module.

A collection lands at `SHA3-256(deployer ‖ ascii(decimal(nonce)) ‖
"qrc721")`, like QRC-20 and QRC-1155 (no height inside).

## Write actions

| action | who | params |
|---|---|---|
| `deploy` | anyone (deployer = owner) | `name`, `symbol` (≤ 64 bytes each) |
| `mint` | collection owner | `collection`, `to`, `id` (decimal, unminted), `uri` (optional, ≤ 2,048 bytes) |
| `transfer` | token owner, its approved address, or an operator | `collection`, `to`, `id` |
| `transfer_from` | same, with an explicit `from` that must be the owner | `collection`, `from`, `to`, `id` |
| `approve` | token owner or an operator | `collection`, `to`, `id` |
| `set_approval_for_all` | any holder, for its own tokens | `collection`, `operator` (≠ caller), `approved` (required bool) |
| `burn` | token owner, approved, or operator | `collection`, `id` |

Ids are strict decimal strings (`parseUint256`). A `collection` that was
never deployed is refused before any action. The fork gate and an unknown
action are HARD; everything else is SOFT.

## Events

Standard signatures, the token id in the value slot:

| event | indexed | data |
|---|---|---|
| `Transfer(sqaddress,sqaddress,uint256)` | from, to | id — `from` is zero on mint, `to` is zero on burn |
| `Approval(sqaddress,sqaddress,uint256)` | owner, approved | id |
| `ApprovalForAll(sqaddress,sqaddress,bool)` | owner, operator | approved |

## Reads (`POST /call`)

| action | params | returns |
|---|---|---|
| `owner_of` | `collection`, `id` | `owner`, `exists` |
| `balance_of` | `collection`, `owner` | `balance` |
| `token_uri` | `collection`, `id` | `uri` |
| `get_approved` | `collection`, `id` | `approved` (zero when none) |
| `is_approved_for_all` | `collection`, `owner`, `operator` | `approved` |
| `token_info` | `collection` | `name`, `symbol`, `owner`, `exists`, `total_supply` |

## Enabling it

```json
"forks": { "module_revert_v1": 1, "qrc721_v1": 1 }
```

## SDK

No `QRC721` Program in `@splendor/sqc-sdk` yet; `wallet.sendModuleCall({
module: 'qrc721', action, params })` reaches every action, and the SDK's
`known-module-actions.json` lists the module with each action as a declared
gap until the client lands.
