# X402: payments, settlement records, and what one payment buys

X402 is the HTTP-402 payment path: a client presents a signed `X-Payment`
header, the node verifies it, the payer-signed `TxX402` settles on chain, and
the resource server serves the request.

Three things are separate and are easy to run together. Keeping them apart is
what the rules below are for.

| | What proves it | Where it lives |
| --- | --- | --- |
| The payment was authorised | ML-DSA-65 signature over the payload | the header |
| The payment settled | `TxX402` in a block + the settlement record | chain state |
| The payment bought this request | the consumption record | the resource server |

## The settlement record (`x402_settle_v1`)

The executor writes an `X402Settlement` (payer, payee, amount, chain, tx hash,
height) keyed by the payment nonce, in the same state write that consumes the
nonce. It exists because a consumed nonce alone says only *that* a payment
happened, not *which*: without it, an already-used payer/nonce presented with a
different claimed payee or amount took the confirmed fallback at
`POST /x402/settle`.

The record is a **state-root leaf**, so writing it is a consensus change and it
is gated on the `x402_settle_v1` fork height:

- before the height, only the used-nonce marker is written — byte for byte the
  registry as it was before the record existed, so a node carrying the record
  code and a node that does not compute the same root and a rolling upgrade is
  safe;
- at the height every node starts writing the record in the same block.

`verify_identity_v1` depends on it (`Schedule.Validate` enforces the order): the
SQVL `x402` spend linkage resolves the record, so a chain enforcing the linkage
before it writes the records would refuse every x402 spend.

A payment settled **before** the activation height has no record. The used-nonce
path at `/x402/settle` cannot confirm it, and answers 402 naming that case. The
receipt path (`settlement_tx` hash → successful receipt) is unaffected and is
still the primary confirmation.

## What one payment buys

`valid_before` is chosen and signed by the payer. Inside that window a settled
payment answers `confirmed` to every presentation of the same `X-Payment`
header, because the chain has no idea which HTTP request is being made. The
header is a bearer credential, so without a record on the server side one
payment buys an unbounded number of requests.

The SDK middleware (`createX402Middleware`) therefore keeps a **consumption
record** binding a payment identity to the request it was spent on.

**Payment identity** is `chain_id | from | nonce` — the tuple the on-chain
replay registry is keyed by, so two headers share an identity iff they are the
same payment.

**Request binding** defaults to `METHOD path`, narrowed by a client
`Idempotency-Key` (or `X-Request-Id`) header when one is present. Supply
`bindRequest` to bind something else — a route template, a resource id, a body
hash the application has already parsed.

### Reuse semantics (the policy, stated)

1. **First presentation** of a payment claims it for its request binding, then
   settles. Access is granted when settlement is established under the
   configured `settlementPolicy`.
2. **Retry of the same binding** replays the grant, within an allowance. It does
   not settle again and does not cost a second payment: a dropped response must
   not charge the payer twice. The allowance is what stops it handing out an
   unbounded number of requests instead — `reuse.maxGrants`, 3 by default, being
   the request that was paid for plus two retries.
3. **Replay past the allowance** is refused with `402 Payment Reuse Exhausted`,
   naming which bound was reached. Two bounds apply, because either alone leaves
   the other axis open: the grant count above, and `reuse.replayWindowMs`,
   3 minutes by default, measured from when the payment was claimed rather than
   from the payer's own authorisation window. `maxGrants: 1` sells strictly one
   request; there is no unbounded setting.
4. **A different binding** carrying the same payment is refused with
   `402 Payment Already Consumed`, and that is checked BEFORE the allowance, so
   a misrouted credential is told where the payment went rather than told to pay
   again.
5. **A settlement that never establishes** releases the claim, so the payer —
   who was not charged — can spend the payment on another request, with a full
   allowance.
6. **Records expire** at the end of the payer's own authorisation window
   (`valid_before` + 60 s skew, clamped to [5 min, 24 h]). Retention is not the
   reuse window: it is how long a *different* binding is refused, which is why it
   outlives the replay allowance. Once the record is gone a replay is refused by
   signature-window validation at the node instead.
7. **Concurrency** is reserve-then-settle, and the allowance is charged at claim
   time rather than at grant: the claim is taken before the settle call, so two
   concurrent requests cannot both believe they own the payment, and ten
   simultaneous replays cannot all read a counter nobody has incremented yet.
8. **A full store refuses** new claims (`503`) rather than evicting a live
   record. Evicting one would hand that payment a second free request.

The store shipped by default is an in-process `Map`, and that bounds what any of
the above can promise: a restart — a rolling deploy included — forgets every
claim, so a payment whose window is still open is claimed again and buys another
allowance, and `k` replicas grant the same payment `k` times. Neither is fixable
inside a per-process store; both are what the pluggable `consumptionStore` is
for, and the policy travels with every claim so a shared store keeps the counter
beside the records. What survives either is the on-chain half: a nonce settles
exactly once, for ever.

These are Stripe's idempotency-key semantics — same key and same parameters
replay the stored outcome, same key with different parameters is an error —
applied to a payment rather than an API key, and they are what the x402
security literature calls pre-grant idempotency on `(payment id, resource id)`.
L402 arrives at the same place from the other direction: its macaroon names the
resource the Lightning preimage pays for, so the credential cannot be carried to
a different endpoint.

### Why the record is off chain

Deliberate, and worth restating because the settlement record next to it *is* on
chain:

- **The chain cannot see the request.** Method, path and body never reach
  consensus. Binding a payment to a request on chain would mean committing a
  request digest inside the signed payment payload — a wire-format change to the
  payload, the settlement transaction and the digest, needing its own fork, and
  still only as good as the resource server's honesty about which request it
  served.
- **The binding is the resource server's policy, not the chain's.** Two servers
  may reasonably scope one payment differently (per endpoint, per resource id,
  per batch). A consensus rule would have to pick one for everybody.
- **Cost.** Every consumption would be another state leaf and another
  transaction, for a fact only one party needs.
- **The chain already enforces the part that must be global**: the payment nonce
  is consumed exactly once, for ever, so a payment cannot be *settled* twice no
  matter how many servers see the header.

### Deployment note

The default store is a per-process `Map`. Behind more than one replica each
replica would grant the same payment once, so a multi-replica deployment MUST
pass a shared `consumptionStore` (Redis `SET NX` gives the same atomic claim).
The interface is three methods — `claim`, `grant`, `release`.

```ts
import { createX402Middleware } from '@splendor/sqc-sdk/x402';

app.use(
  createX402Middleware({
    payTo: 'SQ:…',
    price: '0.01',
    connection,
    consumptionStore: redisConsumptionStore(client), // shared across replicas
    bindRequest: (req) => `${req.method} ${routeTemplate(req.path)}`,
  }),
);
```
