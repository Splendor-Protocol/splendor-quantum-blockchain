# Closing the 2026-09-18 implementation review

**Branch:** `hardening-19` (local; not pushed, not released)
**Reviewed commit:** `e1c23cc` · **Base for this work:** `6e14f56`
**Review:** *Splendor Implementation Status 2026-09-17-3*

The review closed 10 finding groups, marked 1 implemented-pending-activation
and left 10 partial. This document answers its handoff item 5 — *"return each
finding ID with the changed call path and one focused demonstration of the
specific closure condition"* — for every partial item.

Three things to read first, because they bound everything below.

1. **Nothing here is activated.** Every execution and consensus change lands
   behind a fork that no tier schedules. Shipping a release does not turn any
   of it on. `npm run forks` reads the live answer from each tier.
2. **A release blocker was found and fixed during this work**, not by the
   review: `MarkX402NonceSettled` wrote a state-root leaf with no fork
   predicate. It reached `main` after the reviewed commit and would have
   forked a mixed-version validator set at the first x402 transaction. The
   deployed tiers run `v1.1.2` (`feb2ef7`), which predates it, so nothing live
   was ever exposed — but nothing could be released from `main` until it was
   gated. It is gated now, behind `x402_settle_v1`.
3. **Every fix is demonstrated by a test that fails without it.** Where a test
   could pass for the wrong reason it was re-run against the reverted code and
   the failure recorded. Tests that merely reported a finding (`t.Logf`) were
   rewritten to fail on it.

## Per-finding closure

### C1 — Consensus round recovery · was Partial

**Defect, in one sentence:** the engine kept the *fact* of a proof of lock and
threw away the *proof*, which is why all four of the review's bullets were the
same bug.

| | |
|---|---|
| **Call path** | `onPrevoteQuorum` now retains and persists the prevote quorum (a `.pol` sidecar); `RoundChange` carries `LockedCert`/`LockedBlock` outside the signature, so the attachment is strippable but never forgeable; `addRoundChangeLocked` decides justification once, at admission; `safeValueLocked` selects the highest justified lock and `CanPropose` reports that outcome; `castPrevote` records durably *before* signing. Separately fixed: `SetHeight` restored a lock without its round. |
| **Demonstration** | `go test ./consensus -run 'TestTwoPhaseABBLocksConvergeWithFaultySilent\|TestPrevoteSurvivesRestartWithinTheSameView\|TestRoundChangeLeaderProposesHighestJustifiedValue\|TestJournalPrevoteRules'` |
| **Prior art** | Tendermint's PoLC and unlock rule — `LastLockRound < PoLC-Round < R`; the *middle* relation was the one missing here, so a proposal could justify itself. IBFT 2.0 round-change certificates (arXiv:1909.10194), deliberately diverged from: unjustified round changes still **count** toward quorum, because refusing them stalls `n=4, f=1`. HotStuff `highQC` selection (arXiv:1803.05069). CometBFT's `(height, round, step)` signing state, and the 2022 Persistence tombstonings that showed what a forgotten prevote costs. |
| **Still open** | `bft_rounds_v1` is unscheduled on testnet and mainnet. No byte cap on round-change attachments. A leader does not re-validate the body of a proposal it re-proposes. |

### C5 — VM work accounting · was Partial

**Defect:** the child's gas allowance was computed *before* the caller was
charged for copying the call's input, so a child could be handed gas the
parent no longer had.

| | |
|---|---|
| **Call path** | The `CALL` arm is reordered to: pop → decode `argsOffset`/`argsSize` → `chargeCopy(argsSz)` → `callGas = min(requested, gas − gasUsed)` → `mem.load` → dispatch. RPC gained `simEngine`/`simHeight` so `/call` and `/estimate` simulate under the fork rules consensus is actually executing, at head+1. |
| **Demonstration** | `go test ./vm -run TestCallChildBudgetExcludesInputCopyCost` and `./rpc -run TestSimulationUsesConsensusForkRules`. `TestPreForkCallGasOrderingUnchanged` pins that pre-fork execution is bit-identical; the fork moves the parent's total by exactly the copy charge and nothing else. |
| **Prior art** | EIP-150's 63/64 rule, the yellow paper's `C_gascap`, and geth's `gasCall`/`callGasTemp` — which charge the memory and copy cost into `gasFunc` *before* `callGasTemp` is computed. Splendor had the same two steps in the other order. |
| **Still open** | `vm_gas_v1` unscheduled everywhere. Memory expansion for the args range is still uncharged (a pre-existing model difference, not introduced here). `/call` now evaluates at head+1, so `BLOCKHEIGHT` in a view call shifts by one — a release-note item. |

### C6 — Public resource limits and cancellation · was Partial

Two independent halves. Both had a fix land on `main` after the reviewed
commit; both were put under adversarial QA rather than assumed closed. One
held, one did not.

**Half 1 — compiler (`3a355de`): held, with residuals now fixed.** The
acyclic-expansion bomb (2^n) is stopped in 160–310 ms. QA found two residuals:
`addExpr` did not descend into an index expression's *key*, so a call hidden
in `a[f()]` escaped the cycle check entirely; and the budget counted emitted
*items*, not bytes, so a 4 KiB request still peaked at 364–444 MiB.

**Half 2 — trusted proxy (`00f0259`): did not hold.** It took the
**left-most** `X-Forwarded-For` entry. Every appending proxy — nginx's
`$proxy_add_x_forwarded_for`, Cloudflare, cloudflared — preserves what the
client sent and appends its own view on the right, so left-most is precisely
the entry the attacker writes. Reproduced: 50 rotated headers became 50
distinct rate-limit identities against a cap of 2, and an attacker could pin
a *victim's* budget by naming it.

| | |
|---|---|
| **Call path** | `compiler.addExpr` walks `indexExpr.key`; `MaxEmittedItems` became `MaxGenerationSteps`, joined by `MaxAsmItems` and `MaxGeneratedBytes` (512 KiB / 262,144 items). New `rpc/client_ip.go` holds one `ClientIPPolicy` used by **both** `sealedClientKey` and `RateLimiter.clientKey`, so the two planes cannot disagree about who is calling; it walks the chain right-to-left to the first entry no trusted proxy wrote, takes `--trusted-proxy` (IP/CIDR) and `--client-ip-header` (e.g. `CF-Connecting-IP`), namespaces keys `ip:`/`fwd:`, and bounds the parse to 4 KiB and 32 hops. A bad `--trusted-proxy` stops the node at start-up rather than silently widening what a header may claim. |
| **Demonstration** | `go test ./rpc -run 'TestQARotatingForwardedEntriesCannotEscapeTheSourceCap\|TestQAForwardedEntryCannotPinAnotherPeersBudget'` and `./compiler -run TestQA`. Both rpc tests were verified non-vacuous by walking the chain left-to-right again: they fail with exactly the attack they describe. Compiler QA workload: 362–432 MiB / ~250 ms → 21–25 MiB / 22–37 ms. |
| **Prior art** | RFC 7239's right-most-untrusted rule; Envoy's `xff_num_trusted_hops`; nginx's `$proxy_add_x_forwarded_for` (the *reason* left-most is attacker-controlled). |
| **Still open** | Compiler cancellation is still between phases, not within one. |

### R2 — Snapshot session lifecycle · was Partial

**Defect:** completed multi-page sessions stayed pinned; there was no periodic
expiry, so a session was released only when someone asked for it again.

| | |
|---|---|
| **Call path** | A background sweeper runs while anything is retained and stops itself when idle; `Close` stops it outright. The pinned LevelDB snapshot is released the moment the final page is produced — only the page is retained, in a cache bounded by count (16) and total leaf bytes (8 MiB), on the session TTL. A page larger than that budget is not retained at all. A cached page answers **only** the cursor it was produced for, so nothing can splice two roots. |
| **Demonstration** | `go test ./core/block -run 'TestExpiredSnapshotSessionReleasesWithoutAnotherRequest\|TestCompletedSessionUnpinsButKeepsFinalPageRetryable'` |
| **Prior art** | The Cosmos SDK's separation of the *served artifact* lifecycle from the *in-flight restore* lifecycle, and `snapshot-keep-recent`. |

### R3 — Bounded resumable snapshot transfer · was Partial

**Defect:** import built one full in-memory batch, and an expired checkpoint
left the node retrying a checkpoint no peer could serve.

| | |
|---|---|
| **Call path** | Both import forms share one streaming path filling batches to ≤ 8 MiB. A node-local key `meta:import_pending` is written before the first batch and cleared in the batch that writes the height marker, giving three durable states (nothing / unpublished partial / published-and-verified); `meta:` is already outside the state root, excluded from export and refused from the wire, so this is **not** a consensus, state-root or wire change. A height mismatch is now `ErrSnapshotCheckpointUnavailable`, separating "this peer cannot help" from "this checkpoint is gone"; a round where some peer reports the latter and none can continue abandons the staged transfer **wholesale** — head, cursor and leaves, never a subset — and restarts once from scratch. A *completed* download is never abandoned. |
| **Demonstration** | `go test ./core/state -run TestImportSnapshotJSONL` and `./rpc -run TestStateSyncAbandonsACheckpointNoPeerCanServe`. The first failing run imported 525,056 bytes in 1 batch under a 32 KiB budget. |
| **Prior art** | Erigon's staged sync `--batchSize` (fill / flush / restart); geth's moving snap-sync pivot, which retires a stale pivot rather than serving it. |
| **Still open (stated, not fixed)** | What still scales with snapshot size is the leaf-hash index — 32 bytes plus the key per leaf, never values. That is not import overhead: it is the in-memory state the node runs on afterwards, and a node that cannot hold it cannot serve the chain by any sync path. |

### R6 — Receipt indexes and readiness · was Partial

**Defect:** `validator_locked` reflected an apply halt, not the BFT lock or
round, so a deadlocked set looked healthy from outside.

| | |
|---|---|
| **Call path** | Readiness now separates three independent things — apply, sync, and consensus. A `consensusProbe` reports the engine's live height, round and held vote lock, so `/readyz` and `/status` can tell a normal lock from a set that has stopped committing. A node with no BFT engine returns nil and the commit clock answers for progress. The stall threshold sits at ten block intervals (floored at `DefaultStallAfter`), because a view change costs a few round timeouts and is the system working. |
| **Demonstration** | `go test ./cmd/node -run 'TestNodeReadyStatusHealthyWhileConsensusNotProgressing\|TestNodeReadyStatusConsensusProgress\|TestNodeReadyStatusSeparatesApplyRecoveryFromConsensus'` and `./rpc -run TestReadyz` |
| **Prior art** | CometBFT's `/status` `catching_up`; Cosmos's `x-cosmos-block-height`. |

### R7 — Parallel block fetch byte accounting · was Partial

**Defect:** the budget reserved an estimate and corrected it only at ordered
apply, so the real peak was unbounded between the two.

| | |
|---|---|
| **Call path** | Reservation moved into the worker, *before* the read; the read is capped at the reservation (`errFetchBodyTooLarge`, and a new `ErrSealedReplyTooLarge` replacing a silently truncated envelope). Real wire size is charged on arrival and released at apply. The working reservation rises to the largest body actually seen, capped at the budget, so it converges instead of refetching per block. Sealed reads are capped at `sealedWireAllowance` (2× + 4 KiB) with the *decoded* body checked against the allowance. |
| **Demonstration** | `go test ./network -run 'TestHeldOutOfOrderBlocksStayInsideTheByteBudget\|TestOversizedBlockSyncsUnderTheDocumentedException\|TestFetchReservationConvergesOnRealBlockSizes'`. First failing run held 76,253 bytes against an 8 KiB budget. |
| **Prior art** | geth's downloader: a `resultSize` EMA plus a byte ceiling, and the head-of-queue item never throttled. |
| **Documented exception** | The single height the applier is waiting for is admitted over the allowance. Making it wait is a deadlock, not backpressure; heights dispatch in ascending order so that worker always exists, and the overrun is at most one block. |

### I1 — Proof and state-view consistency · was Partial

**Defect:** account reads included pending state, the proof's block hash was
fetched separately, and simulation ran against a moving view — three ways for
one query to answer from two different states.

| | |
|---|---|
| **Call path** | New `core/state/view.go`: `CommittedHead{Root, Height, HeightKnown}` via `CommittedHeadView()`, and a `CommittedView` holding a pinned LevelDB snapshot so every part of one answer comes from one state. Failure returns `ErrNoCommittedView` — there is no silent fallback to a speculative view, because answering from the wrong state is worse than not answering. `Simulate()` split into `SimulateCommitted()` and `SimulateSpeculative()` so the choice is made at the call site and is visible. |
| **Demonstration** | `go test ./rpc -run 'TestStateAccountNeverServesPendingOverlayAsCommitted\|TestStateProofBlockHashIdentifiesTheProofRoot\|TestCallViewIsCommittedUnlessAskedOtherwise\|TestSimulateCommittedFailsClosedOnAClosedDB'` |

### I4 / I5 — x402 confirmation and SQVL settlement identity · was Partial, prioritised

Four separate defects, one of them a release blocker.

| | |
|---|---|
| **Release blocker** | `execX402` wrote the `x402settle:<key>` state-root leaf with **no fork predicate** (root `f0631ff9…` → `6941a278…`). Now behind `x402_settle_v1`, threaded exactly like `vm_gas_v1`: `NewExecutor` installs `SetX402SettleRules`, `execX402` consults it and otherwise falls back to `MarkX402NonceUsed`, byte-identical to the pre-change registry. `Schedule.Validate` gained a dependency — `verify_identity_v1` requires `x402_settle_v1` no later than itself, because the SQVL linkage resolves the record, and a chain enforcing the linkage first would refuse every x402 spend. |
| **Confirmation reuse** | The used-nonce fallback could confirm a different, unauthenticated claimed payment. Consumption is now a resource-server concern: a payment identity (`chain_id\|from\|nonce`) is claimed for a request binding *before* settling (reserve-then-settle); the same binding replays the grant, a different binding gets `402 Payment Already Consumed`, a failed settlement releases the claim. Off-chain deliberately — the chain never sees method, path or body, and the global part (a nonce settles once, for ever) is already enforced on-chain. |
| **Linkage** | `applyX402SettlementLinkage` required neither payee nor amount, so a proof that simply *omitted* them was accepted against any settled payment for that nonce. It now requires both and compares the whole tuple through `X402Settlement.Matches` — the same comparison the settle handler uses. Both fields are inside the v2 digest, so the payer's signature covers what the proof asserts. |
| **Identity gating — REVERSED, see the second pass below** | This row originally read: *"`verifyDeploy`/`verifySetOperator` now parse **and** persist operator identities only under `verify_identity_v1`."* That gate was itself the divergence and has been removed. v1.1.2 — which every tier runs — parses and persists both unconditionally, and `verify_v1` is at height 1 on every genesis while `verify_identity_v1` is scheduled nowhere, so gating them made a hardening-19 node write a different instance leaf, and a different state root, than the fleet. Recording from the module's own activation is what the deployed build does and is the key-registration migration the review asked for. |
| **Demonstration** | `go test ./core/block -run 'TestX402SettlementRecordIsForkGated\|TestVerifyIdentityRequiresSettlementRecords'` — verified non-vacuous by forcing the write back on, which fails it. `./vm -run TestQAX402LinkageRequiresThePayeeAndTheAmount` — 7 shapes refused, the honest instruction still accepted. `./rpc -run 'TestQAFabricatedRetryCannotClaimRealPayment\|TestQAUsedNonceChangedDetailsNeverConfirms'` for the chain-side confirmation. Consumption is an SDK concern and is demonstrated there: `npm test -- x402-middleware` in `sdk/sqc-sdk` — 25 replays across different request bindings grant exactly one. |
| **Deliberately unchanged** | `TestQAOneSettledPaymentConfirmsUnlimitedRequests` still reports that the chain confirms a settled nonce for any number of requests, and that is correct: the chain never sees a method, a path or a body, so it cannot bind a payment to a request. What the chain enforces is the global part — a nonce settles once, for ever. The per-request part is enforced by the resource server, which is the only party that knows what was asked for. |
| **Prior art** | The x402 v2 specification; *Five Attacks on x402* (arXiv:2605.11781); *Free-Riding the Agentic Web* (arXiv:2605.30998); L402; Stripe's idempotency keys; and OpenEthereum's post-Berlin consensus split — the canonical demonstration of what one ungated state change does to a mixed-version network. |
| **Still open** | `x402_settle_v1` is unscheduled on every genesis. Pre-activation, `/x402/settle`'s used-nonce path cannot confirm from a bare nonce — deliberate and fail-closed; the error names the case. Request-bound *signatures* (a resource digest inside the signed payload) would need their own fork. Payments settled before activation have no record. |

### RLNC — chain binding and publication lifecycle

The review kept RLNC out of the numbered findings and listed seven things
still required to call it integrated. **Two are closed here; five are not, by
design.**

| | |
|---|---|
| **Item 3 — bind descriptors to a chain** | `Descriptor.DescriptorID()` derived its identifier from the anchor, height, codec and generation shape. None of those named the network, so a manifest published on devnet verified and decoded byte-for-byte on mainnet — and because `codebook.go` hashes that id into every symbol leaf specifically to stop cross-manifest replay, the symbol binding did not separate tiers either. `Anchor` gained a `ChainID`; the descriptor preimage is now domain-tagged (`SPLENDOR-QC-OBJDESC-v2`) and length-prefixed with the chain id outermost. `NewSender` stamps the id from the node's own adopted identity and refuses a caller naming another chain; `NewReceiver` refuses a foreign manifest with `ErrWrongChain` *before* consulting the signer — because the same operator key legitimately exists on more than one tier, so authorization answers "who sent this" and never "which chain is this from". |
| **Item 5 — refresh published snapshots** | The hub served the first object it ever published until the process restarted, so a joiner was handed a state root that aged every block. `Put` now retires the previous object instead of deleting it: it stays addressable by its own descriptor id, bounded to 2 retired generations and a 2-minute TTL, so a fetch already in progress completes against the manifest it verified — the old behaviour failed every remaining symbol with "no coded object published", discarding a verified manifest and saying something untrue while doing it. `ensurePublishedSnapshot` republishes once the chain is 128 blocks past what is published; `publishSnapshotObject` no longer carries its own "something is already published" check, which had silently turned every refresh into a no-op. |
| **Wire compatibility** | This is a **breaking change to the SQCO format**, taken deliberately because the live path is off by default on every tier. `WireVersion` goes 1 → 2. A version-1 frame carries no chain id and there is no safe way to read one — assuming the local chain is exactly the replay this field prevents — so a v1 frame is refused by version with `ErrUnknownWireVersion` rather than being read optimistically. |
| **Demonstration** | `go test ./network/objects -run 'TestManifestFromAnotherTierIsRefused\|TestDescriptorIDSeparatesTiers\|TestHubDoesNotTearAnInFlightFetch\|TestHubRetirementIsBounded'` and `./cmd/node -run TestEnsurePublishedSnapshotRefreshesAsTheChainAdvances` |
| **Prior art** | EIP-155 — this is exactly its bug class (a signed object valid on one network replayed on another because the signed bytes never named the network) and exactly its fix. CometBFT appends `ChainID` to every `CanonicalVote`'s `SignBytes` for the same reason. For the lifecycle half: geth returns a distinct `ErrSnapshotStale` from an invalidated layer rather than quietly answering from stale state, and the Cosmos SDK keeps recent snapshots rather than dropping one the instant the next is taken. |
| **Still open, by design** | Items 1, 2, 4, 6 and 7: `FetchCodedObject` still has no real block/snapshot sync caller, decoded bytes are not yet connected to block/QC or snapshot-root validation, and there is no capability negotiation, peer failover, per-peer budget or uncoded baseline benchmark. The accurate description remains **partial live integration** — off by default, not consumed by normal sync. |

## Activation — the distinction that matters most

The review refused to accept a repository-reported deployment state as
evidence, and it was right to. Installing a release activates nothing; genesis
decides. The readme had said `bft_rounds_v1` was *"unscheduled on every public
tier today"* — written once, then aged: devnet now sits on a genesis that
schedules it at height 1, so the sentence was false for a third of the fleet
while it stood in the readme *and* in the published validation report.

`npm run forks` now reads each tier's effective schedule from its own
`/status`, takes the fork **names** from `core/forks/forks.go` so a rule that
exists in code but nowhere in the fleet is still listed, and probes twice so a
hostname answering from two chains is visible rather than averaged.

Read live on 19 September 2026:

| Rule | Devnet | Testnet | Mainnet |
|---|---|---|---|
| `bft_rounds_v1` | genesis | — | — |
| `validators_admission_v1` | genesis | **—** | genesis |
| `vm_gas_v1` | — | — | — |
| `vm_call_v1` | — | — | — |
| `verify_identity_v1` | — | — | — |
| `x402_settle_v1` | — | — | — |
| `min_fee_v1` | — | — | — |

`npm run forks -- --check` enforces the one invariant the tier table already
promises in prose — testnet is *"mainnet's rules plus what mainnet has not
adopted yet"* — for consensus and execution rules only, since application
modules are tier-local by design. **It fails today:** mainnet enforces
`validators_admission_v1` and testnet does not, so the next promotion
rehearses on rules mainnet is not using.

Consequence for the fixes above: **C5, I3, I4/I5 and the C1 two-phase path are
inert on testnet and mainnet until someone schedules them.** They are correct
and tested; they are not in force.

## Documentation reconciliation

The review's five documentation items, each closed:

- **Contradictory RLNC claims.** Two passages said "library and benchmark
  only" while a third correctly described the optional serving path. All three
  now say the same thing: partial live integration, behind `--object-codec`,

## What this branch does not do

- **It is not pushed and not released.** Local `hardening-19` only.
- **It schedules no fork.** Every activation is an operator decision that
  needs a coordinated height per tier.
- **It does not make RLNC a sync transport.** Five of the seven requirements
  remain open and are listed above.
- **It does not fix the testnet/mainnet admission divergence** that
  `npm run forks -- --check` reports — that is an operations decision.
- **CI reliability:** the consensus tests are timing-sensitive and flake under
  full `go test ./...` parallelism; they pass with `-p 4` or run alone. Worth
  pinning in CI before this is trusted as a gate.

## Second pass — an adversarial review of this branch, 19 September 2026

Everything above was written by the work it describes. It was then reviewed
adversarially against the original document, and the review did not accept it.
Eleven findings followed, of which one was a release blocker of the same class
this branch had itself been created to fix. All are closed below, each with a
regression test that was checked by reverting the fix and observing the failure.

### The blocker: a gate that was itself the divergence

`904d25e` gated operator-identity persistence behind `verify_identity_v1`. The
reasoning — honouring the field early would write a record an older build does
not — had the fleet backwards. v1.1.2 (`feb2ef7`) parses and persists both
`operator_identities` and `slh_pubkey` unconditionally; `verify_v1` sits at
height 1 in both genesis documents and `verify_identity_v1` in neither. So the
gate, not the recording, made a node on this branch write a different instance
leaf — and accept a malformed key the fleet rejects. `verifyDeploy` and
`verifySetOperator` are now byte-identical to `feb2ef7` outside the checks that
genuinely belong to the identity fork.

The lesson is narrower than "gate state changes". It is that *whether* a change
diverges is a question about the deployed fleet, not about the code, and it can
only be answered by diffing against what the fleet runs.

A residual, stated rather than fixed: node releases before v1.1.0 had no
identity field at all and dropped the payload key silently. Devnet and testnet
were upgraded in place, so replaying history from that window with any v1.1.x
build records identities the original execution did not. That divergence arrived
with v1.1.0, and re-adding a gate would trade it for a worse one against the
current fleet. Settling it means scanning those journals for verify-module
transactions before the v1.1.0 rollout height.

### The other ten

| Finding | What was wrong | Closed by |
|---|---|---|
| C1 restart | `SetHeight` resumed from the precommit journal alone, so a node that prevoted at round ≥ 1 and crashed came back where its own body is refused, armed no timer, and emitted no round-change — halting a four-validator set with one silent member | resume at the durable prevote's round; a refusal that is not the restart shape marks the view so the timer arms |
| C1 round-change body | `ComputeVotedHash` covers the header alone, so a genuine certificate carrying a garbage transaction list was justified and re-proposed | the whole body is validated, and a value the leader did not build is checked against its producer's signature and the head it would apply to |
| C1 retention | attachments were kept for all 33 admissible rounds for the whole height, each up to a block in size | unjustified and far-ahead records are stored without their proof or body; stale rounds are dropped on every view change; ingress bounds a round-change before decoding |
| R6 probe | readiness took the engine lock, which is held through the executor's entire block apply — 15s for a 4,173-transaction block | one snapshot published at each transition, so a probe cannot stall behind an apply |
| R6/I1 root | every reader of the committed root rebuilt it: sort every key, hash twice per leaf, and again under the executor's exclusive lock when behind head | the root is cached beside the index it describes, written in the same critical section, invalid by default so a missed site is slow rather than wrong |
| R3 restart | the abandon policy acted on an unauthenticated height, discarding a transfer an honest peer was still feeding — and the caller retries every two seconds | a lower height is no longer a stale claim; acting on a higher one is gated on the transfer having stood still all round; the count is bounded and persisted |
| R3 session | a session's expiry was fixed at creation, so a transfer longer than the TTL lost its session and had the mismatch reported as the checkpoint being gone | the TTL runs from the last page served; an idle session still expires on the same clock |
| R7 budget | a body too large to fit widened the allowance ×4 and fed that guess back as a measurement, so two such replies walked the reservation to the whole budget and sync ran serial | only bodies that arrived are learned from, with headroom over the measurement; a reply that cannot be a valid block costs its peer preference |
| RLNC retirement | the retired-generation TTL was two minutes while a fetch may run for ten, and a refresh fires every four | the TTL is the fetch cap, pinned by a test in the package that owns the deadline |
| I4 reuse | one settled payment served unbounded replays of its request binding for up to 24 hours | a grant allowance charged at claim time, with both a count and a window; exhaustion is its own error |

Smaller items closed alongside: the justified-value selection no longer falls
through to map order; a round-change quorum for a later round advances the view
instead of being walked to one timeout at a time; the simulation height comes
from the pinned view rather than a second read of the executor; IPv6 budgets
aggregate to /64; an unattributable forwarded chain is refused rather than
re-keyed as the proxy; the bare `--trust-proxy` form warns at start-up; the
compiler's statement walk fails closed on a form it does not know; a
confirmation names the transaction that actually settled; `/balance` and
`/nonce` say that they read pending state; and the final-page cache's count and
byte bounds agree with the size of a page.

### On the tests

Two test defects were found in the work above and are worth recording, because
they are the same defect.

`TestVerifyIdentityPreForkInstanceLeafMatchesDeployedBuild` derived its expected
leaf with `json.Marshal(verifyInstance{...})` — the struct it was checking — so
the encoding cancelled out on both sides. Swapping two fields changes the real
leaf, and would split a mixed-version set at the first verify deploy, and the
test still passed. It compares literal wire bytes now.

`TestHubDoesNotTearAnInFlightFetch` never advanced the hub's clock, so it could
not observe an expiry at all; and the first replacement for it advanced by
`RetiredTTL`, the constant under test, so it moved with the bug and passed at two
minutes as happily as at ten.

An expectation computed from the thing under test is not an expectation. Both
now use written-out values.

### What this pass does not change

- Still not pushed, still not released. Local `hardening-19`.
- Still schedules no fork. Every activation remains an operator decision.
- Still does not make RLNC a sync transport: five of the seven requirements are
  open, and off by default.
- Still does not fix the testnet/mainnet admission divergence that
  `npm run forks -- --check` reports.
- The snapshot import still holds the state mutex for its duration, so the state
  endpoints block during one. Documented as a known characteristic rather than
  changed.

## Third pass — a second independent audit, 20 September 2026

The branch was audited again, by a different reviewer on different
infrastructure. Six findings, four of them serious, and all six were real. They
are closed in `d76899b`, `ddf3ee1` and `c64355f`, each with a regression test
checked by reverting the fix.

What is worth recording is that **three of the six were in the second pass's own
work**, and one was older than either pass.

### The stall the second pass created, and half-inherited

`SetHeight` assigned `currentRound` directly. It is the only place the engine
moves a round without `enterRoundLocked`, which signs a round-change and sends
it — so a node recovering above round 0 sat in a view no peer knew about, armed
no timer because it holds no proposal there and may lead it, and never announced
itself afterwards. The quorum at that round was then permanently one member
short.

The second pass introduced this for the prevote path. The precommit path — the
branch's original C1 work — had it already. Both are fixed by the same line.

Convergence, since a fix that only sends a message would not be one:
`enterRoundLocked` records the node's own round-change as well as broadcasting
it, so the recovered node counts toward the quorum at its round while the peers
still walking up through their timeouts arrive. Announcing at round 0 is
deliberately excluded, or every restart would push the set forward a view.

### Four ways round a bound that had just been added

The reuse allowance the second pass added could be avoided entirely.

The identity was the wire spelling. On chain a payment is a hash over decoded
bytes, and both the address and the nonce are hex — decoded case-insensitively,
and the SDK's own decoder strips `0x`. So `ab…`, `AB…` and `0xab…` are one
payment to the node and were three records here, each with a full allowance.
Re-encoding the header bought exactly the requests the allowance existed to
refuse.

`release` took only a payment id, so a replay that held no reservation could
delete the record the request still settling depended on.

Retention is clamped to a day, so a payer signing a longer window got a record
that expired while the payment was still good — and the node cannot refuse the
next presentation, because the nonce really did settle.

And a settle call that threw released nothing and answered "Malformed X-Payment
header": a grant spent, nothing served, and the caller blamed.

The pattern across all four: the bound was enforced at one point and the state it
depended on was reachable by another route. A limit is only as narrow as the
identity it is keyed by, the ownership of the thing it reserves, and the lifetime
of the record that holds it.

### The oldest one

`trust` was computed as `trustProxy || len(trustedProxies) > 0`, read before the
loop that skips blank entries. One blank — a trailing comma, an unset variable
expanded into the flag — turned trust on with an empty prefix list, and an empty
prefix list means every peer is a proxy. So `--trusted-proxy ""` honoured the
forwarded header from anyone, silently, since the bare-flag warning could not
fire either.

### On the reported hang

The same audit reported the Go suite hanging in `./consensus`. It does not: the
package takes about 145 seconds and passes at `-p 4` and at CI's default
parallelism, verified three times each with a 600-second limit. That runtime is
the thing to know about before treating the suite as a gate — it looks like a
hang to anyone expecting seconds.

### What the three passes have in common

Every pass found real defects in the pass before it, and each time the defect was
of a kind that pass had just been reasoning about. The x402 state-root leaf was
found while hardening x402. The identity gate was added while thinking about
divergence, and was itself a divergence. The reuse bound was added and then
walked round four ways. The lesson is not that any pass was careless: it is that
a fix is not evidence about its own correctness, and neither is the test written
beside it by the same hand.

**Three defects were found in the reconciliation itself**, none visible on
either branch alone:

- The multi-generation **receiver had no chain check at all** — and that is the
  receiver the coded snapshot path uses by default, so the gap sat on the road
  that actually carries state.
- `ObjectManifest.ObjectSize` drives `Join`'s final truncation and was in no
  preimage: a field deciding how many bytes the receiver keeps, covered by no
  signature.
- Both of `main`'s snapshot import paths assign `s.leaves` directly, and
  neither knew about the committed-root cache `hardening-19` added, so after
  the merge an import published the root of the state the node had **before**
  it. Both import tests caught it.

**The benchmark claim was corrected rather than repeated.** Review item 7 asks
for an uncoded baseline with selective retransmission; there was none, and the
headline "coded 30/30, uncoded 0/30" describes a transport that gives up after
one pass. With `--retransmit-rounds 4` the uncoded baseline reaches every trial
too, on slightly **fewer** bytes (669,822 against 672,164) and about a third of
the authenticate CPU. What coding buys is **round trips** — one pass against
four — which is a latency argument, and a good one for a join across a 200 ms
link. It would not justify coding on a LAN. Saying so is worth more than a
favourable comparison against a strawman, for a default that is now on.
